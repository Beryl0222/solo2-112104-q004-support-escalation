# 多轮客服对话的承诺边界与升级处置

本项目整理企业支持团队把跨渠道对话交给不同班次处理。客户在一轮对话里谈及两个订单，后续用“这个”指代其中一个；只做句级意图分类会把退款请求、物流咨询和已作出的客服承诺错误合并，造成接班人员重复承诺或遗漏升级。

工具是**只读**的：读取合成对话、合成政策库和订单快照，生成可追溯的整理结果，**不会发送任何客户答复**。

## 快速开始

```bash
# 文本报告（按客户事项组织）
python3 -m support_dialogue data/support_conversation.json \
    --policies data/policies.json --orders data/orders.json

# 指定单个客户事项
python3 -m support_dialogue data/support_conversation.json \
    --policies data/policies.json --orders data/orders.json --matter matter-2

# 机器可读输出
python3 -m support_dialogue data/support_conversation.json \
    --policies data/policies.json --orders data/orders.json --format json

# 测试
python3 -m unittest discover -s tests -v
```

只依赖 Python 3.11 标准库。输入格式错误时命令返回码为 2，并给出中文错误说明。

## 数据文件（全部为合成演练资料）

| 文件 | 内容 |
| --- | --- |
| `data/support.json` | 原始 4 轮最小样例（网页 + 邮件补充） |
| `data/support_conversation.json` | 13 轮跨渠道对话：两个订单、代词、补正、取消、仅表达不满、重复承诺 |
| `data/support_ambiguous.json` | 指代歧义、客户否认退款、多单合并承诺、客户复述承诺 |
| `data/support_policy_update.json` | 旧政策下已承诺，新政策生效后窗口收紧 |
| `data/policies.json` | 合成政策库（退款两个版本、物流、取消、投诉关怀） |
| `data/orders.json` | 合成订单快照（只含被明确断言过的字段） |

对话记录字段：`id`、`text` 必填；`channel`、`turn`、`speaker`、`timestamp` 可选。出现未知字段会被拒绝（避免把未经核实的推断混入报告）。

## 输出内容

每个**客户事项**（matter）包含：

- 关联订单、事项状态、给下一班的下一步建议；
- 识别出的**诉求**：意图、订单归属依据（原句指明 / 代词解析 / 未确定）、原话与轮次；
- **政策核对**：当前结论、逐条条件（满足 / 不满足 / 资料缺失）、政策原文引用、订单补正原话、历史核对记录；
- **承诺**：原文、确认轮次与确认时间、承诺时限、确认时适用政策版本、是否为重复表述 / 已被后续口头调整；
- **升级**：团队、状态（建议升级 / 处理中 / 已完成 / 需人工复核）、原因与相关原话；
- **需追问**：面向客户的问题与需内部补录的资料的区分。

报告末尾统一列出待追问项与升级进度。`DialogueLedger.locate(evidence)` 返回 `记录号#turn-轮次@起始:结束`，可直接定位回原句字符区间。

## 关键规则

1. **订单归属优先于句级意图。** 同一轮里“订单 A 物流、订单 B 退款”会各自成事项；订单不同或意图不同不会合并。句内后续分句可沿用本句已点名的订单。
2. **代词只在唯一时可解析。** 解析顺序：同句明确订单 → 同意图已有订单 → 全对话唯一订单。多于一个候选时不开猜，生成“具体指哪个订单”的追问，并列出候选。
3. **补正会重新核对，但不覆盖历史。** 订单字段变化后，未完成诉求新增一次 `order_updated` 核对；旧核对对象冻结保留。已确认承诺永远不被改写。
4. **承诺是不可变快照。** 记录原文、确认轮次、确认时间与当时适用政策版本。新政策到达只新增核对；接班人员重复同一句话会记为 `repeated` 并指向首条承诺，不重新计时；不同说法会新增记录，并把旧记录标为 `adjusted`。
5. **政策允许 ≠ 本单符合条件。** 每条条件按订单字段逐项判定；任一条件不满足即为 `eligible=no`，结论中明确写出“政策允许不等于本订单符合条件”。
6. **不满 ≠ 赔付请求。** 只有含明确诉求的分句才建退款诉求；纯不满建为投诉事项，且没有订单时只问“涉及哪个订单”，不做政策裁定。
7. **资料缺失必须给出具体追问。** 每个政策条件自带 `prompt` 与 `audience`（问客户 / 内部确认），缺失时原样呈现，而不是笼统要求“补充资料”。
8. **升级需要条件满足或坐席明确转交。** 建议升级与已转交分开记录；新政策使订单不再满足条件时，原升级保留并转为“需人工复核”，原因原文与复核提示同时保留。

## 代码结构

```
support_dialogue/
  ingest.py     读取记录、校验字段、生成字符级证据
  text.py       分句、意图/承诺/时限等确定性识别
  policy.py     政策加载、版本选择、逐条件判定
  analyser.py   逐轮状态机：诉求、订单归属、承诺、补正、升级
  models.py     不可变数据对象与查询辅助
  report.py     文本报告
  __main__.py   CLI
```

`ConversationAnalyser(turns=..., policies=..., orders=...)` 可直接在代码中复用于批处理；`analyse_file()` 是文件入口。

## 已知边界

- 识别基于关键词与固定规则，面向本仓库的合成语料；新渠道/新说法需扩充 `text.py` 的线索表。
- 不推断订单字段：只有对话或订单快照明确给出的事实才参与政策判定，其余一律作为缺失追问。
- 时间仅用于政策版本选择；不推断“今天”对应的具体日期。
